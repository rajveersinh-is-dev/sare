# Adversarial Review C — Systems & Experimental-Performance Reviewer

Project: SARE (Safe-Reduction + Adaptive elimination ordering), candidate C1.
Reviewer persona: systems and experimental-performance reviewer.
Mandate: audit baseline selection/configuration; look for measurement artifacts, unfair comparisons,
compilation effects, caching, cherry-picking; verify reported numbers are regenerable; check
memory/runtime honesty; scaling, repetition, uncertainty; workload representativeness; clean-
environment reproducibility.
Label: INTERNAL ADVERSARIAL REVIEW (not peer review).

---

## 1. Hardware / software environment recorded

- CPU: 11th Gen Intel i5-11260H, 6 cores / 12 threads @ 2.60 GHz.
- RAM: ~15.7 GiB.
- GPU: Intel UHD + NVIDIA RTX 3050 Laptop (NOT used; CPU-only comparison). Good — avoids
  GPU-acceleration confounds.
- Python 3.14.6, Rust 1.98.1; benchmarks run the Rust release binary (opt-level 3, LTO).
- OS: Windows 11.

Environment metadata is recorded (PROGRESS.md). Machine-specific details (exact CPU model, RAM)
are present. Good.

## 2. Baseline selection and fairness

Baselines: min-degree, min-fill (reimplemented in the SAME Rust binary as SARE), plus
sare-a0/sare-a2/sare-lookahead ablations. All six algorithms share the same binary, same
compiler flags, same machine, same input parsing. This is a FAIR same-language comparison — no
"compiled vs interpreted" confound. Good.

Limitation: AMD itself (SuiteSparse) was not directly benchmarked; min-degree/min-fill are
stand-ins. AMD is the strongest widely used baseline; min-degree/min-fill are reasonable but not
identical to AMD. The claim "comparable to min-degree/AMD" should be qualified as "comparable to
min-degree/min-fill (stand-ins for AMD/MD/MF)."

Baselines were not deliberately misconfigured; all use the same elimination cost model. Fair.

## 3. Measurement methodology

- Timing: time.perf_counter around the subprocess call (includes process startup + ordering;
  does NOT include Rust compilation, which is prebuilt). Process startup (~ms) is included in
  elapsed_s — for small graphs this is a nontrivial fraction. This slightly inflates all times
  equally; acceptable but should be noted.
- Each instance run ONCE (no repetition). No confidence intervals, no bootstrap, no variability
  measurement. This is a weakness: run-to-run noise (OS scheduling, CPU turbo) is not captured.
  For a defensible benchmark, each (instance, algorithm) should be run N>=5 times and report
  mean + CI.
- No warm-up / cache policy specified. Not critical for these small graph orderings but worth
  documenting.
- Memory usage is NOT measured. The complexity analysis states space bounds but no empirical
  peak memory is reported. Weakness.
- No outlier exclusion (none needed since N=1, but with repetition a policy would be needed).

## 4. Benchmark suite representativeness

Instances: paths, cliques, stars, trees, grids, Erdős-Rényi (sparse/dense), chordal graphs;
sizes n up to 500 (full run). Fixed seeds, deterministic generation. Good — reproducible.

Missing: real-world sparse matrices (SuiteSparse University of Florida collection). Plain edge
lists cannot encode isolated vertices (n must be inferred from max edge vertex); Matrix Market
headers carry n but were not used for real matrices. This limits external validity — results on
synthetic graphs may not transfer to real sparse matrices. The suite is "randomly generated +
structured" but not "realistic workloads from the intended application" (sparse direct solvers).

Cases that disadvantage SARE are included (all cases, since SARE doesn't win anywhere clearly).
No hand-picked cherry-picking detected — the full suite is reported.

## 5. Regenerability

- scripts/run_benchmarks.py regenerates results/raw/benchmarks.csv from scratch.
- results/processed/summary.csv and relative_to_sare.csv regenerated from raw.
- figures regenerated by the same script (matplotlib Agg).
- Raw CSV present. Commands documented. The Rust binary must be prebuilt (`cargo build --release`).
- The exact commit associated with results is NOT recorded (no git repo yet / no result-commit
  traceability). Weakness for reproducibility.

## 6. Statistics and uncertainty

- Single run per (instance, algorithm). No mean over repetitions, no confidence interval, no
  standard deviation. The numbers are point estimates; uncertainty unknown. This violates the
  "repeated measurements and robust summary statistics" guideline.
- Geometric mean not used (good — only per-instance ratios).
- Individual workloads reported alongside aggregates (good).

## 7. Honesty of reported results

- Results include cases where SARE loses (slower, equal or worse fill). No unfavorable results
  removed. Good.
- The `nan` fill ratios (fill=0, division by zero) are present in the CSV — honestly recorded,
  not hidden.
- The absolute timings are small (0.01–2.7 s) and dominated by process startup + O(n·m) ordering;
  the time differences between algorithms are real but small in absolute terms.

## 8. Clean-environment reproducibility

Not yet tested from a clean environment (no git repo/published repo yet). The documented
workflow: `cargo build --release` then `python scripts/run_benchmarks.py`. Python reference also
available. Dependencies: Rust toolchain only for the CLI; Python reference needs no external
deps beyond stdlib. Reasonably reproducible.

## 9. Verdict for this persona

**Strengths:** fair same-language baseline comparison; reproducible generation with fixed seeds;
full raw data + regeneration script; honest reporting of losses; no cherry-picking; CPU-only
avoids GPU confounds.

**Weaknesses:** single run per instance (no uncertainty/CI); no memory measurement; no real-world
SuiteSparse matrices (synthetic only); process startup included in small-graph timings; result-
to-commit traceability not yet established; AMD not directly benchmarked.

**Strongest defensible statement:** SARE is comparable in fill quality to min-degree/min-fill
(stand-ins for AMD) but slower, measured on synthetic instance families with fixed seeds, single
runs, CPU-only. Uncertainty not quantified.

## 10. Required fixes before publication

1. Run each (instance, algorithm) N>=5 times; report mean + 95% CI (bootstrap or t-interval).
2. Measure and report peak memory (e.g., /usr/bin -v equivalent on Windows, or a Rust-side
   allocator probe).
3. Add a few real-world sparse matrices (Matrix Market, n from header) to the suite.
4. Record the git commit associated with the reported results.
5. Clarify that timings include subprocess startup; consider timing the ordering kernel only.
6. Qualify the baseline as "min-degree/min-fill (stand-ins for AMD/MD/MF)."
